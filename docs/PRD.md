# PRD：Yuki 接入 Minecraft（分层 Agent）

版本 v0.3 · 2026-10-30 · 状态：体验方向已调整，计划待实施
适用范围：本地离线服实验环境（`server/` :25565 主世界，`server-test/` :25566 实验场）

---

## 1. 背景与目标

把已有的人格 Agent「Yuki」（Python，独立仓库 `/home/asumi/Yuki`，QQ 场景已稳定运行）接进 Minecraft，让她以玩家身份活着、听得懂自然语言、能完成多步委托，并保持人设不降智。

**已确认的技术地基（本文件写作时的实测结论，不再重复论证）**

| 项 | 结论 |
|---|---|
| mineflayer | 开源 MIT，4.39.0；协议最高支持 26.1（775），与本地 `26.1.2-Fabric` 客户端一致；26.2（776）不支持 |
| 插件 26.1 兼容性 | pathfinder / collectblock / pvp / tool / armor-manager / auto-eat / statemachine 全部实测可用 |
| 不可用 | prismarine-viewer 渲染上限 1.21.4 → 26.1 无法 headless 渲染 |
| 截图方案 | 官方客户端 spectator 观战 + `ffmpeg x11grab` 系统级抓帧（X11 :0.0 已实测出图）；观战视角是否跟随 Yuki 尚未验证；**不开发 Fabric Mod** |
| 硬件 | 无 NVIDIA GPU，内存紧张 → L2 必须走云端 API，实时运动闭环留在 Node 本地代码 |

**目标**

1. Yuki 能在 MC 里被自然语言指挥，完成多步委托。
2. 长任务期间不阻塞、可被打断，并能继续陪玩家聊天。
3. 人设不退化：L1 输出自然语言，不碰执行器 JSON 或报错堆栈。
4. 底层动作复用 Mineflayer 生态；实时控制由 L3 本地代码负责。
5. **让 Yuki 拥有有连续性的游玩经历**：注意到世界变化，选择值得关注的事；需要时主动获取一张视觉证据；由她决定回应、行动、记住或忽略。

**核心原则**：不持续截图、不把 LLM 当传感器。Mineflayer 负责结构化感知，代码负责聚合与注意力筛选，视觉只在有必要时使用，L1 保留最终意愿判断。允许无所事事和不行动。

**非目标（明确不做）**

- 不开发 Fabric Mod，不做反编译/Java 开发。
- 第一版不做 `smelt`（熔炉 GUI 交互），不做附魔、酿造、红石。
- 不做长期世界地图 / 矿点记忆 / 建造成本模型。
- 不做多 bot、不做语音、不做模型微调。

## 2. 架构

保留 L1/L2/L3，在 L3 与 L1 之间增加体验编排层（Experience Orchestrator），第一版作为 Node 侧车内部模块，不新增进程。

```text
Minecraft 世界
  │ Mineflayer 结构化事件 / 任务结果
  ▼
L3 Sidecar
  ├─ World Observer：采集低成本事件
  ├─ Event Grouper：把连续变化聚合为候选经历
  ├─ Salience Scorer：新颖性、兴趣、重要性、重复与打断成本
  ├─ Attention Scheduler：忽略 / 记录 / 唤醒 / 申请截图
  └─ Snapshot Scheduler：按需截图，异步执行
        │ 压缩后的 Experience Capsule
        ▼
L1 Yuki：理解、表达，决定是否观察/靠近/记住/忽略
        │ 只有决定行动时
        ▼
L2 规划器 → L3 技能与状态机

Experience Memory：文字经历 + 事件元数据 + 可选截图引用
```

**职责边界**

- **Sidecar**：持有 bot、状态机、技能、守护逻辑和体验编排；tick 级逻辑留在本地。
- **World Observer**：仅采集 Mineflayer 已能可靠获得的结构化变化。
- **Event Grouper**：合并连续、相邻、同源变化；例如搭建筑过程中不得逐方块唤醒。
- **Salience Scorer / Attention Scheduler**：分别决定是否记录、唤醒 L1、请求截图；这三个阈值不能混为一谈。
- **Snapshot Scheduler**：截图开关、配额、稳定窗口与失败降级；不得阻塞任务、聊天或守护逻辑。
- **L1**：对压缩后的经历做反应并决定是否行动；体验编排层不能替她做价值判断。
- **L2**：仍只做自然语言到有序步骤的翻译，不持有意愿或世界注意力状态。

截图链路必须先验证 spectator 客户端是否跟随 Yuki 位置与朝向。`bot.lookAt()` 改变 bot 朝向，不代表外部观战客户端一定同步。若不同步，P4 无视觉闭环仍继续；截图暂时限定为人工触发或固定镜头。

## 3. 已冻结的接口契约

### 3.1 L1 → L2 / L3：意图

```jsonc
{
  "intention_id": "uuid",
  "priority": 0,                  // 0-8；9 保留给守护逻辑
  "text": "去挖一点石头，烧成平滑石头",   // 自然语言，允许含糊
  "deadline_s": 180               // 可选，超时算 failed
}
```

### 3.2 L2 → L3：步骤列表（表达力受限，不允许 if/loop/DAG）

```jsonc
{
  "intention_id": "uuid",
  "priority": 5,
  "steps": [
    { "skill": "mine", "args": { "block": "stone", "count": 5 }, "on_fail": "retry" },
    { "skill": "goto", "args": { "x": 12, "y": 64, "z": -8, "range": 2 }, "on_fail": "abort" },
    { "skill": "deposit", "args": {} }
  ]
}
```

- `priority` 0–8（9 保留给内部守护逻辑，直投一律 400）。
- `on_fail` 仅允许 `retry` | `abort` | `skip`。
- 技能白名单（P1 实测口径，`deposit` 不给坐标=找 16 格内最近的箱子/木桶）：

| skill | args | 硬校验 |
|---|---|---|
| `mine` | `block`, `count` 1–64 | 背包内该方块掉落物增量（查 `block.drops`） |
| `goto` | `x`,`y`,`z`,`range` 0–3 | 水平距离 ≤ range+1 且垂直差 ≤ 2 |
| `follow` | `player`,`seconds` 3–300（**可选，不给=持续跟随直到被取消/抢占/跟丢**）,`distance` 1–6 | 跟随时与目标的最大距离 |
| `craft` | `item`,`count` 1–64 | 产物背包增量；自动补中间产物（木板/木棍/工作台），3×3 时自己造并放下工作台，缺材料返回 `missing_material` |
| `place` | `item`,`x`,`y`,`z`（可选，缺省放脚边） | 世界里真的出现了该方块 |
| `deposit` | `x`,`y`,`z`（可选，须同时给）,`item`（可选）,`count`（可选） | 背包对应物品实际减少量 |
| `attack` | `target`（实体 ID 或 `hostile`）,`count` 1–8 | 目标实体从世界消失 |
| `eat` | `food`（可选） | `bot.food` 数值上升 |
| `equip` | `item`,`destination`（hand/off-hand/head/torso/legs/feet） | 目标槽位里的物品名 |

- L2 输出必须过 JSON Schema 校验，非法即拒收并降级为"失败上报"，不允许把脏 JSON 塞进执行器。

### 3.3 L3 → L1：回调与事件

```jsonc
// 任务终态
{ "type": "task_done", "intention_id": "uuid", "status": "done|failed|aborted",
  "summary": "挖了 20 块石头，已经放进家门口的箱子" }

// 世界事件（第二档感知）
{ "type": "event", "kind": "hurt|low_health|nightfall|player_near|new_building|path_fail",
  "severity": 0-9, "detail": {...} }
```

// 体验编排层完成筛选后，才允许把压缩经历交给 L1
{ "type": "experience", "experience_id": "uuid",
  "kind": "construction_candidate|new_entity|landmark_arrival|task_milestone",
  "summary": "附近出现了一处可能值得观察的变化",
  "salience": 0.82, "visual": "none|attached|unavailable",
  "options": ["react", "observe", "approach", "remember", "ignore"] }
```

原始事件、坐标、方块清单留在 L3。`summary` 必须是短人话；`options` 只是可选提示，并允许不行动。

### 3.4 L3 → L1：临时状态注入（ephemeral status）

**原则**：L1 每次调用 LLM 都必须知道"我现在在干什么"，但这份状态**只在本次调用有效**，调用结束即失效；每次调用重新注入最新值，不写进对话历史、不累积、不复述。

```
【当前状态·仅本次有效，不要复述此段】
status=working
task=挖圆石 12/20
note=正在下矿洞，视野很差
```

字段固定为四项，避免模型自由发挥：

| 字段 | 取值 |
|---|---|
| `status` | `idle` / `working` / `fleeing` / `fighting` / `stuck` / `dead` / `resting` |
| `task` | `技能名 进度/总数`，无任务则 `none` |
| `note` | ≤ 30 字的一句人话补充（危险来源、位置特征、L3 已采取的措施） |
| `reply` | `need` / `no_reply` |

**注入规则**

1. **单槽 latest-wins**：同一时刻只有一份状态，新的覆盖旧的，不允许排队堆积。
2. **搭车优先**：只要本次调用是因为玩家说话、任务回调等真实事件发起的，状态就附加在同一次调用里，零额外成本。
3. **静默唤醒**：只有 `severity ≥ 7` 且 L1 已闲置超过阈值时才独立唤醒一次；该次调用的输出**丢弃不上屏**，只把一句话写进内心记录/日记，避免重复唤醒。
4. **`reply=no_reply`** 用于"受击逃跑了""被怪打死了已复活""路被堵住正在绕"这类无需她下令、也无需她开口的情形。此时状态里必须写明 L3 已采取的措施，例如：
   `status=fleeing / note=被僵尸围攻，正在逃跑并回击，不用你下指令`
5. **死亡**：复活后注入 `status=dead` + `note=刚刚死了，复活点已回`，若 Chat 通道已有系统死亡提示则不重复注入。
6. **新鲜度**：状态来自 L3 `/state`，超过 3 秒取不到则标注 `note=状态可能过期`，不允许静默沿用旧值。

**为什么这么设计**：L1 的回答质量取决于"她知不知道自己此刻在干嘛"。把状态做成一次性注入，既让她每次都知道当前处境，又不会像历史消息那样越堆越长、把上下文和成本吃干。

### 3.5 优先级规则

| 优先级 | 归属 | 行为 |
|---|---|---|
| 9 | 守护逻辑（硬编码） | 受击、低血、脚下岩浆、饥饿临界 → 立即中断当前任务，逃跑/进食/补血 |
| 0–8 | L1 声明 | 新意图 priority > 当前 → 抢占；等于 → 抢占（人设优先）；小于 → 排队（队列上限 3） |

### 3.6 上下文预算：三层结构

L1 的每次调用只允许由三层内容拼成，**任何一层都不能无限长**：

| 层 | 内容 | 预算 | 生命周期 |
|---|---|---|---|
| 常驻层 | 人格 prompt + 临时状态注入（3.4）+ 心愿 top1 | ≤ 400 tokens | 每次重建，永不累积 |
| 轮内层 | 最近 `KEEP_LAST_DIALOGUE` 轮对话（复用现有 `history_dict` 切片） | 现有配置 | 滚动 |
| 按需层 | 记忆/日记检索命中（`【回忆】` 前缀，≤3 条） | 命中才注入 | 单次 |

**硬规则**

- MC 的原始事件流、坐标列表、完整背包表**禁止进 L1**——那些是 L2 的输入，进 L1 会立刻把人格淹掉。
- 事件播报进 L1 前必须压成人话（"有个玩家在你旁边盖房子"），原始 JSON 留在 sidecar。
- 长期记忆按**世界分区**落在 `planner/state/worlds/<world>/`（`chat_id=mc:<world>`，见 HANDOFF 决策 #30–#32）：对话 `history.json`、日记/事件 `memory.jsonl`、向量索引 `chroma/`；召回算法照搬 Yuki 的 `modules/memory/rag.py`。

### 3.7 体验闭环：注意力、经历与主动感知

**体验闭环**：

```text
世界变化/任务结果 → 聚合成候选 → 评分与去重 → 记录/唤醒/可选截图
→ L1 自主反应或忽略 → 可选行动 → 形成经历记忆
```

- **评分维度（第一版规则化、可解释）**：新颖度、惊奇度、兴趣关联、社交显著性、进展意义、重复惩罚、可信度和打断当前活动的代价。先用配置权重，不训练模型。
- **分级门槛**：低门槛记录，高门槛唤醒 L1，更高门槛才申请截图。忙于玩家委托或反射时，普通经历延迟或只记录。
- **候选事件**：初遇实体、连续人工方块变化聚类、新地点/环境到达、任务里程碑。仅报告候选，不靠方块 ID 断言“这是爱心/房子”。
- **L1 选项**：react、observe、approach、remember、ignore；允许 `no_action`。只有行动才进入现有 intention → L2 → L3 链路。
- **经历记忆**：保存时间、世界、事件类型、压缩摘要、评分、L1 反应、后续行动与结果；截图只作为可选引用，不自动塞入每轮上下文。
- **长期兴趣、心愿单、mood、漫游锚点**暂不作为 P4 前置条件；在体验闭环跑通后再根据实际游玩反馈决定是否需要以及如何实现。

### 3.8 开发期开关（必须有）

| 指令 | 作用 |
|---|---|
| `yuki stop` | 硬停：自主循环、任务、播报全部停止，bot 待机 |
| `yuki play on/off` | 只开关自主玩耍，不影响接活 |
| `yuki rest <分钟>` | 休息：除 `severity ≥ 7` 外一律不唤醒 |

调试阶段默认 **`play off`**，稳定后再常驻开启。所有自主唤醒都有预算上限，超出即静默。

### M0 · 竖切片（已完成 ✅ 2026-10-28）

**目标**：用最小的代价打通整条链路，最早暴露假想错误。**不追求技能齐全。**

链路：公屏一句中文 → L2 出步骤 → L3 执行 → 硬校验 → 回调 → 她用自己的人设语气汇报。

范围：`sidecar` 骨架（`/intention` `/cancel` `/state` `/events` `/say`）+ 三个技能（`mine` `goto` `follow`）+ 硬校验 + `POST /plan` + L1 人格层（`send_intention` 工具调用）+ 状态注入。

**落地形态（与原设计的差异）**：本阶段**不接 Yuki 本体**（机主决定：本 Bot 与 Yuki 的关联仅是 prompt 一致）。L1 人格与 L2 规划在本仓库新建的 `planner/`（Python）里独立实现，Node 侧车只做执行。公屏通道为侧车 `POST /chat` + `POST /say`。

验收（已全部实测通过）：① 她说人话回应用户；② 挖到 ≥3 石头；③ 完成后自然语言汇报且无 JSON；④ 挖矿途中仍能聊天；⑤ 单任务 API 调用 ≤ 4 次。

**不做**：craft / deposit / smelt / 事件播报 / 自主性 / 视觉 / 多玩家权限。

详见 `HANDOFF.md` 第 3 节。

### P1 · 侧车状态机与技能库（无 LLM）

**目标**：不接任何模型，纯脚本驱动就能把"多步任务"跑完。这一阶段决定整个系统的工程质量。

**交付**
- `sidecar/`：常驻 Node 服务，暴露本地 HTTP/WS
  - `POST /intention` 接收 3.2 的结构化步骤列表（此阶段由测试脚本直接发）
  - `POST /cancel {intention_id}`
  - `GET /state`（位置、血量、饥饿、背包摘要、当前步骤、队列）
  - `GET /events`（SSE/WS 推送）
- 技能库：`mine / craft / goto / follow / attack / eat / equip / deposit`，每个技能统一签名
  `async function(args, ctx) -> {ok, detail}`
- 状态机：顺序执行步骤 → 每步结束**硬校验**（方格增量/到达判定/实体消失）→ 失败按 `on_fail` 处理
- 守护逻辑（priority 9）：受击检测、血量阈值、岩浆/虚空检测、饥饿，触发即抢占
- 任务取消：pathfinder goal 清空 + collectblock 中止 + 控制状态复位

**验收**
1. 脚本发 `[{mine stone 5}, {goto 家}, {deposit}]` → 全程无人工干预完成，日志逐步 PASS
2. 执行中调 `POST /cancel` → 1 秒内 bot 停止移动，任务状态 `aborted`
3. 人为从高处摔落触发低血 → 守护逻辑抢占，正在跑的任务变 `aborted` 并上报
4. 连续 10 次同类任务成功率 ≥ 8/10（固定场景）

**落地状态（2026-10-28 完成，`bash scripts/p1-run.sh` 19/19 通过，全程不调模型）**

- 已交付：守护逻辑（受击/低血/岩浆/虚空/饥饿，priority 9，抢占后 `aborted` 上报 + 保命动作）、8 个技能、队列语义（同级抢占 / 低优先级排队上限 3 / priority 9 拒收）、取消兜底复位（goal/collectblock/pvp/容器/控制状态）、三套固定场景（空地 / 树林 / 矿洞）
- 验收对照：①mine→goto→deposit 全链路 185 件入箱 ②取消后 1 秒内 idle（实测 2–28ms）③受击与低血守护均抢占并上报 ④空地 goto 10/10
- `craft` 已支持 **3×3**：需要工作台时会自动合成并放下；配方递归解析（木板→木棍→工作台→工具）为自写小模块，不引第三方合成库
- `place` 技能补齐；`mine` 对需要工具才能掉落的方块（如石头）先查 `harvestTools`，缺工具直接返回 `missing_tool`，不再交给 collectBlock 空转
- `deposit` 支持"给坐标"或"自动找 16 格内最近容器"；容器类型 chest / trapped_chest / barrel
- 端到端实测：背包只有原木 → `mine oak_log` → `craft wooden_pickaxe` → `mine stone` 全链路跑通（工作台自动放置）

### P2 · L2 规划器（已完成 ✅ 2026-10-28）

**目标**：中文自然语言 → 合法步骤列表，能自我修正；做不了时把**结构化事实 + 可选方案**交回 L1，由 L1 决定改主意（见 HANDOFF 决策 #22）。

**交付**
- `POST /plan {text, state, last_failure?}` → 3.2 的 steps（云端 API，`disable_thinking=true`）
- JSON Schema 校验 + 一次自动修复重试（把 schema 错误回灌）
- 硬校验失败的**升级路径**：连续失败 2 次才携带"期望 vs 实际"回灌 L2 重规划，最多 2 轮
- 单任务预算：token 上限、时间上限、`retry` 次数上限（默认 2）
- 提示词资产：技能清单 + 参数 schema + 世界状态摘要格式

**验收**
1. "去挖 20 个圆石" → 生成合法 steps 并执行成功，10 次 ≥ 7 次（固定场景）
2. 故意给不可达目标（如"去挖钻石"但周围无矿）→ 系统在 2 轮重规划后返回 `failed` 且给出人话原因，不卡死
3. 输出非法 JSON 的比例 < 5%，且全部被拦截未进入执行器

**约束**：L2 不允许"发明技能"；未知技能名一律拒收。这一阶段不允许 L2 发起截屏。

**落地状态（2026-10-28 完成）**

- 实现在 `planner/`：`l1.py`（Planner + Chain 失败升级）、`budget.py`、`facts.py`、`schema.py::validate_options`、`prompts.py::REPLAN_SYSTEM/OPTIONS_SYSTEM`
- 验收：①挖 20 圆石 **7/10**（3 次为机主在服里打她触发守护抢占，非执行失败；10/10 均生成合法 `mine stone count=20`，平均规划 0.95s）②远古残骸不可达：2 轮自动重规划 + 1 轮 L1 协商，18.8s 回 idle 并给出人话原因 ③真实规划 24 次 **0 非法 JSON**，单测 28/28（13 类非法计划全拦截）
- 单任务预算实测：6 次调用 / 5134 token / 17s（上限 10 / 12000 / 300s）
- 额外补：`POST /dispatch` 调试通道（跳过人格措辞，仍走完整预算与升级链）；L3 增加整条委托时间上限；确定性错误不重试
- 追加：`/state` 暴露附近玩家（真实 ID + 坐标），「过来」翻译为 `goto` 玩家坐标；失败事实可直接用于协商（扁平回调也能提取）
- 追加：`follow` 改为持续动作（不占满整条委托的时间预算），任务终态释放委托上下文；实测 20s 后仍在跟、新委托即时抢占、结束后 `chains=0`

### P3 · L1 与当前基础能力（已完成，细节以 HANDOFF/Log 为准）

**目标**：建立可与玩家交互、能调用身体、能从任务与事件中恢复的 L1 基础。

已落地：本仓库独立 L1（不接 Yuki 本体）、自然语言 + intention 工具、任务完成/失败回调、临时状态注入、`rest` 与低优先级事件聚合、按世界分区的对话/日记记忆；另有 idle tick 与 `roam` 等基础能力。近期 L2 分域专家、15 项技能、四态反射机属于能力扩充。

**边界**：有 idle tick 或 roam 不等于体验闭环完成；事件聚类、注意力筛选、经历关联和按需视觉仍待实现。

### P4 · Experience Loop：无视觉体验闭环（当前实施阶段）

**目标**：让 Yuki 能从结构化世界变化中获得可选择的经历；不依赖持续截图。

#### P4.0 先行验证：截图观战链路

- 起服、sidecar 与原版 spectator 客户端；让 Yuki 移动并改变朝向，人工确认截图是否跟随位置和视角。
- 记录画面来源、同步情况、延迟与失败模式。
- 若不同步，先将截图限制为人工触发/固定镜头，不阻塞无视觉闭环。

#### P4.1 经历数据结构与落盘

- 定义 Experience / Experience Capsule、来源、生命周期、去重键与世界分区存储。
- 原始事件留在 L3；L1 只接收压缩摘要。
- 测序列化、去重、过期、长度限制与重启恢复。

**验收**：重启后经历仍在；同一事件不会无限重复；L1 输入始终是压缩摘要。

#### P4.2 World Observer 与 Event Grouper

第一批覆盖高可信低成本事件：附近初遇实体、短时间空间相近的人工方块变化、环境/地点变化候选、任务里程碑。先不做复杂建筑识别，也不直接声称识别出具体造型。

**验收**：连续放置一组方块只产生一个候选；重复事件合并或抑制；事件处理不阻塞 tick、任务执行与守护。

#### P4.3 Salience Scorer 与 Attention Scheduler

- 配置化规则评分：novelty、surprise、interest、social salience、progress、重复惩罚、interruption cost、confidence。
- 分别配置记录、唤醒和截图门槛。
- 玩家正在交互、高优先级任务或反射期间，普通事件延迟或只记录。
- 可选择 `record_only` / `ignore`，不强制 L1 表态。

**验收**：重复事件不反复唤醒；高价值候选能唤醒；低价值事件只记录；正常任务与守护无明显延迟。

#### P4.4 Experience Capsule 接入 L1

- 将事件压成一两句人话，附有限选项与不行动选项。
- 复用现有 L1 事件路径，不新增第二套人格循环。
- L1 可选择表达、观察、靠近、记住或忽略；行动仍走既有 intention → L2 → L3。
- 任务结果、探索结果都能形成经历；失败不按 KPI 告警，不强迫汇报。

**验收**：初遇实体、建造候选、任务里程碑至少各完成一次“发现 → L1 反应或忽略 → 经历记录”；外部指令可立即接管低优先级体验行动。

---

### P5 · Active Perception：按需视觉闭环

**目标**：结构化信息不足且值得观察时，Yuki 才获取视觉证据。

#### P5.1 Snapshot Scheduler

截图默认关闭；启用后配置最小间隔、每小时配额、同一事件最多一张。建造事件需等待稳定窗口；任务/守护期间默认延迟。截图异步执行，失败降级为无图经历。

#### P5.2 Vision Adapter

截图与 Experience Capsule 绑定，调用现有视觉通道；返回短摘要、置信度与可选标签。视觉不可用时保留结构化候选，不阻塞其它链路；截图不自动进入长期对话上下文。

#### P5.3 主动观察

只有在视角链路已验证后，才尝试转向目标或靠近后截图。若 spectator 不跟随 bot 朝向，降级为固定镜头或人工触发。

#### P5.4 端到端体验验收

玩家在 Yuki 附近完成一颗爱心或其它明确造型：变化被聚合为候选；达到门槛并稳定后最多申请一张截图；视觉结果绑定经历；L1 自主选择表达、观察、靠近、记住或忽略；文字经历保存视觉摘要、截图引用、反应和后续结果。视觉识别失败仍保留无图候选。

体验评估关注是否在有意义的时刻偶尔产生自然反馈、是否不刷屏/不打断；不要求每次触发或每次都识别正确。

---

### P6 · 连续经历与稳定性

- 根据 Yuki 多次实际选择逐步形成兴趣偏好；避免单次行为永久改变权重。
- 评估是否需要心愿单、mood、地点关联和漫游锚点，再决定具体设计。
- 增加 P1–P5 回归、掉线缓存、权限、观测面板、世界备份和长时间运行测试。
- P4/P5 通过后再考虑默认开启自主游玩。
