# 技能开发指南 —— 怎么给 Yuki 加一个新动作

写给以后要加技能的人（包括我自己）。加技能最容易踩的不是写代码，是**漏改一处**：planner 放行、执行器不认识，
或者反过来。这份文档把"必改的五个地方"和"怎么验证没漏"固定下来。

---

## 一、一个技能是什么

技能是**执行器里一个纯函数**，模型看不见它，只剩一句话进、一份事实出：

```js
// sidecar/skills/<名>.js
async function run (args, ctx) { ... }
module.exports = { name: '<名>', run }
```

返回值的形状是硬约定，全仓一致：

```js
// 成功
{ ok: true,  detail: { /* 给 L1 看的、也确实发生过的事实 */ } }
// 失败
{ ok: false, detail: { error: '<上面固定的一张表里的名字>', ...能解释清楚的事实 } }
```

`detail` 会一路走到 `tasks.js` 的 `summarize()`，被翻成一句人话交给 L1（"烧出了 3 个铁锭"）。
所以 **`detail.error` 不是给你看的，是给 `summarize` 和失败协商看的**——名字要稳定，不要随手编。

## 二、必改的五个地方

| # | 文件 | 改什么 | 漏了会怎样 |
|---|---|---|---|
| 1 | `yuki-bot/sidecar/skills/<名>.js` | 技能本体 | — |
| 2 | `yuki-bot/sidecar/skills/index.js` | `require` + 塞进 `SKILLS` 表 | 执行器报 `unknown_skill` |
| 3 | `planner/schema.py` | `SKILLS` 加名字 + `_normalize_step` 加 `elif` 分支 | L2 写得出，planner 先拦下：`skill 不在白名单` |
| 4 | `planner/prompts.py` | `SKILL_LINES` 一行参数说明 + `SKILL_EXAMPLES` 一条真例子 | L2 不知道有这个技能，或参数编错 |
| 5 | `planner/domains.py` | 放进哪几个域的 `skills`；必要时加 `keywords` | L2 在这个域里看不到它；或路由永远选不中这个域 |
| 6 | `yuki-bot/sidecar/tasks.js` | `summarize()` 加一个 `else if` | 她只会说"xxx 没成功" |

第 6 处不改不会出错，但技能就哑了——**这是最容易被忘的一处**。

加完跑一遍，任何一处漏了都会红：

```bash
node yuki-bot/scripts/skills-test.js                 # 执行器侧：表、注册、摘要
/home/asumi/miniconda3/envs/yuki/bin/python planner/tests/test_domains.py   # planner 侧：说明/例子/域/白名单一致性
```

`test_domains.py` 里有一项会**直接读 node 的 `SKILL_NAMES` 跟 planner 白名单对比**，两边漂移立刻报错。

## 三、`ctx` 里有什么

```js
ctx = {
  link,          // 到 bot 的门面，见下
  signal,        // AbortSignal：随时可能被抢占，长循环里必须查
  timeoutMs,     // 这一步的时限（默认 120s）
  progress,      // (done, total) => void，报进度用
}
```

`link` 上真正好用的就这几样：

| 成员 | 作用 |
|---|---|
| `link.bot` | mineflayer 实例，**绝大部分活直接调它** |
| `link.mcData` | 这个版本的 minecraft-data（方块/物品/实体/食物表） |
| `link.pos()` | 当前坐标 `{x,y,z}` 或 `null` |
| `link.gotoNear(x,y,z,range)` | 设一个静态 GoalNear（**不要**用 dynamic goal，pathfinder 在动态 goal 下不放 `goal_reached`） |
| `link.goalReached(ms)` | 等它走到，`{ok, reason}`；带停滞看门狗 |
| `link.ready` | 连接是否就绪 |

常用写法（几乎每个技能都是这个开头）：

```js
const { link, signal } = ctx
const bot = link.bot
if (!bot || !bot.entity) return { ok: false, detail: { error: 'bot_not_ready' } }
if (signal.aborted) return { ok: false, detail: { error: 'cancelled' } }
```

走到目标旁边：

```js
const dist = bot.entity.position.distanceTo(block.position)
if (dist > 3.5) {
  await link.gotoNear(block.position.x, block.position.y, block.position.z, 2)
  const reached = await link.goalReached(15000)
  if (!reached.ok) return { ok: false, detail: { error: 'cannot_reach_x', distance: Math.round(dist) } }
}
```

## 四、三条纪律

**1. 不信"动作没报错"，只信世界变了。**
mineflayer 的 `placeBlock` 会因为"没等到 blockUpdate"抛错，但方块其实放下了；`withdraw` 可能静默失败。
所以每个技能末尾都要**回读世界/背包**再判成败——`mine` 比背包增量，`place` 用 `waitForBlock`，`smelt` 数成品。

```js
const before = countOf(bot, product)
// ... 干活 ...
const smelted = countOf(bot, product) - before
return { ok: smelted > 0, detail: { smelted } }
```

**2. 失败要给"能照着做的下一步"，不是错误码堆。**
`missing_tool` 要带上 `needs: ['stone_pickaxe']`；`no_fuel` 要让人知道"去找木头或煤"。
L2 的重规划靠这些字段，L1 的道歉话术也靠它。

**3. 有些核心 API 是"发完包就不管"的。**
`bot.mount`、`bot.dismount`、`bot.attack`、`bot.swingArm` 都是**同步返回、不 Promise**（返回 `undefined`），
它们只是发了一个包。别写 `await raceTimeout(bot.mount(e), 5000)`——`bot.mount(e)` 是 `undefined`，会当场炸。
正确做法是发完**自己轮询状态**：

```js
bot.mount(entity)
const deadline = Date.now() + 5000
while (Date.now() < deadline && !bot.vehicle) await sleep(100)
```

反过来，下面这些在源码里就是 `async function`，是真 Promise，可以放心 `await` / `raceTimeout`：
`bot.activateBlock`、`bot.activateEntity`、`bot.sleep`、`bot.fish`、`bot.openFurnace`、`bot.openEnchantmentTable`、
`bot.openAnvil`、`bot.openVillager`、`bot.collectBlock.collect`、`bot.consume`、`bot.equip`、`window.deposit`、`window.withdraw`。

**判据只有一条**：去 `node_modules/mineflayer/lib/plugins/*.js` 里看它是 `async function` 还是 `function`。别凭感觉。

**4. 只做一件事，不替 L2 拿主意。**
挖就挖，不顺手捡；烧就烧，不顺手做镐。组合交给 L2 的多步规划。
例外只有一种：**完成这件事本身必需的动作**（烧之前要放熔炉、开门之前要走到门口）。

## 五、域怎么归

`domains.py` 里一个域 = 一组技能 + 一段专家册。归域的标准不是"功能分类"，是**这句话会怎么说出口**：

- 玩家说"挖铁矿做把铁镐" → 路由到 `gather`，而这条链需要 `mine`、`smelt`、`craft`，所以 `gather` 必须**同时**含这三个，
  否则 L2 会写出域外的 `craft` 被 schema 拒掉。
- 一句话命中多个域时按 `_PRIORITY`（craft > combat > interact > gather > travel）取第一个。

加一个新域的门槛很高：**只有当现有域装不下这套知识，或关键词必然打架时**才开。
一般都往现有域里塞。

## 六、参数校验（`schema.py`）

L2 的 JSON 是模型编的，会错。`_normalize_step` 的职责是**在进执行器之前把脏东西拦掉**：

- 字符串统一走 `_str(...)`（去空白、限长）
- 整数走 `_int_range(...)`（`True` 会被当成布尔拒掉）
- 坐标统一走 `_coords(args, index)`（x/y/z 要么全给要么全不给）
- 越界、类型错、未知字段一律 `SchemaError`

拦截率是有测试守着的（`test_p2.py` 的 ① 组）。

## 七、测试怎么写

不需要服务器。`yuki-bot/scripts/skills-test.js` 里加三块：

1. **纯表**：如果技能里有写死的表（配方、燃料、方块名），直接把表测了
2. **早退路径**：造一个假 `ctx`，把 `bot_not_ready` / `cancelled` / 缺参 / 未知物品 / 没有材料 这些分支跑一遍
3. **摘要**：喂一条 `detail` 给 `summarize()`，断言吐出来的那句人话

假 ctx 长这样（照抄 `skills-test.js` 里的 `fakeCtx`）：

```js
const fakeCtx = (items) => ({
  link: {
    mcData: { itemsByName: { /* 用到的几个 */ }, blocksByName: {} },
    bot: { entity: { position: { distanceTo: () => 1 } }, inventory: { items: () => items }, findBlock: () => null }
  },
  signal: { aborted: false },
  timeoutMs: 120000
})
```

真正要让技能"动手"的那部分（放方块、开窗口、时序）只能起服验，见文末。

## 八、完整例子：上船（`mount`）

"上船"这件事核心已经给了，不需要插件：`bot.mount(entity)` / `bot.dismount()` / `bot.vehicle` / `bot.moveVehicle(left, forward)`。
它和 `use` 的区别是：`use` 是对着东西按右键，`mount` 是**坐上去**——门和按钮用 `use`，船、矿车、马用 `mount`。

### 1. `sidecar/skills/mount.js`

```js
'use strict'
// sidecar/skills/mount.js —— 坐上/下来：船、矿车、马。硬校验看 bot.vehicle 是不是真的换了。
const { sleep } = require('../util')

// 能坐的东西：名字从 mcData 里现推，别写死——每个版本都会加新木种的船
const VEHICLE_RE = /(_boat|_minecart|^minecart$|^horse$|^skeleton_horse$|^donkey$|^mule$|^llama$|^pig$|^strider$)/

function isVehicle (entity) {
  return Boolean(entity && entity.name && VEHICLE_RE.test(entity.name))
}

/** mount / dismount 都是发完包就不管的：发完自己等状态变了。 */
async function waitFor (predicate, ms) {
  const deadline = Date.now() + ms
  while (Date.now() < deadline) {
    if (predicate()) return true
    await sleep(100)
  }
  return predicate()
}

async function mount (args, ctx) {
  const { link, signal } = ctx
  const bot = link.bot
  if (!bot || !bot.entity) return { ok: false, detail: { error: 'bot_not_ready' } }
  if (signal.aborted) return { ok: false, detail: { error: 'cancelled' } }

  const target = String(args.target || '').trim()

  // 下来：不给 target，或给了 off
  if (!target || target === 'off' || target === 'dismount') {
    if (!bot.vehicle) return { ok: true, detail: { note: 'not_riding' } }
    const was = bot.vehicle.name
    bot.dismount()
    const off = await waitFor(() => !bot.vehicle, 5000)
    return { ok: off, detail: { dismounted: was, error: off ? undefined : 'still_riding' } }
  }

  if (bot.vehicle) return { ok: false, detail: { error: 'already_riding', vehicle: bot.vehicle.name } }

  const entity = bot.nearestEntity((e) => isVehicle(e) && (!target || e.name === target))
  if (!entity) return { ok: false, detail: { error: 'no_vehicle', target } }

  const dist = bot.entity.position.distanceTo(entity.position)
  if (dist > 3) {
    await link.gotoNear(entity.position.x, entity.position.y, entity.position.z, 2)
    const reached = await link.goalReached(12000)
    if (!reached.ok) return { ok: false, detail: { error: 'cannot_reach_vehicle', distance: Math.round(dist) } }
  }

  const before = bot.vehicle
  bot.mount(entity)
  const on = await waitFor(() => bot.vehicle && bot.vehicle !== before, 5000)
  return {
    ok: on,
    detail: { vehicle: bot.vehicle ? bot.vehicle.name : entity.name, error: on ? undefined : 'not_riding' }
  }
}

module.exports = { name: 'mount', run: mount, isVehicle }
```

## 九、起服真验

纯逻辑测完只算一半。让技能真的动手，要起服：

```bash
bash scripts/world-up.sh          # 主服 :25565 + planner :8791 + sidecar :8790
bash scripts/world-down.sh        # 收工务必优雅停服
```

看日志：

```bash
grep step_done /tmp/yuki-world/sidecar.log | tail -5
```

`step_done` 那行里有 `ok`、`detail`、`elapsed_ms`——`detail` 是判"技能说得对不对"的唯一依据。

## 十、反射不是技能

`guardian.js`（打/跑/吃）和 `mlg.js`（落地自救）**不走上面那套流程**：它们不经 L2、不进 `schema.py` 白名单、
不占技能编号，是身体自己的状态机。加反射的门槛比加技能高——反射会抢占任务，写错了会一直抢。
判据：**这件事模型想清楚就晚了**（摔死、被打死、掉岩浆），才做成反射；其余都做技能。

## 附录：往哪加、值不值得加

按"核心给不给 API"分三档。**别去找插件**：插件生态覆盖的是"运动与工具选择"（寻路、选镐、挖一整簇），
游戏内容基本都在核心，找不到就是没有。

### A 档：核心直接有，20–60 行

| 功能 | 核心 API | 价值 |
|---|---|---|
| 上船/矿车/骑马 `mount` | `bot.mount` / `dismount` / `vehicle` | 高：现在没法跟玩家一起坐船 |
| 钓鱼 `fish` | `bot.fish()` | 中：食物来源，也是"陪玩"的动作 |
| 附魔 `enchant` | `bot.openEnchantmentTable` + `.enchant(i)` | 中：铁镐之后自然要附魔 |
| 铁砧改名/合并 `anvil` | `bot.openAnvil` + `.rename` / `.combine` | 中 |
| 村民交易 `trade` | `bot.openVillager` + `.trade(i, n)` | 中：换绿宝石 |
| 写告示牌/写书 | `bot.updateSign` / `bot.writeBook` + `signBook` | 低但便宜 |
| 捡地上的掉落物 `collect` | `mineflayer-collectblock`（已装） | 中：现在只有 mine 会顺手捡自己挖的 |

### B 档：要自己拼 `clickWindow`

切石机、织布机、信标、酿造台、合成器——没有现成 API，得知道每个界面的槽位含义（numen 为此写了一整套 `MenuKind`）。
**建议先做 A 档的 `enchant`/`anvil`/`trade` 三个（有现成封装），确认真有人用再考虑通用 GUI 技能。**

### C 档：组合型，先别做

种植/收割、繁殖动物、盾牌格挡、拉弓蓄力、鞘翅滑翔。
这些不是"一个动作"，要么需要持续状态机（拉弓蓄力、盾牌），要么 L2 用 `use`+`place` 组合就能凑合。

### 不建议

- **命令方块**（`bot.setCommandBlock`）：要 op，能改世界规则，风险远超收益。
- **酿造**：配方链长、收益低，等有人真的要用再说。
